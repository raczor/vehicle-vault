Concepts, in plain words

Each card says what the idea means, then where it lives in this repo.

Row-level security (RLS)

What it means: the database itself decides which rows a connection may see or change. Even if application code forgets a WHERE tenant_id = ..., Postgres still filters. A bug in the service becomes an empty result, not a data leak.

Each transaction first tells Postgres who is asking, then a policy on the table compares every row to that value:

select set_config('app.tenant_id', '<tenant uuid>', true);   -- true = this transaction only

CREATE POLICY vehicles_tenant_isolation ON vehicles
  USING      (tenant_id = nullif(current_setting('app.tenant_id', true), '')::uuid)
  WITH CHECK (tenant_id = nullif(current_setting('app.tenant_id', true), '')::uuid);

Three details make it hold up:

  • The app connects as a role that does not own the table (app_user). Table owners skip RLS unless it is forced (FORCE ROW LEVEL SECURITY), and superusers and BYPASSRLS roles skip it always, so the service must never connect as any of them.
  • It fails closed. If no tenant is set, the setting is empty, the comparison is NULL, and no row matches.
  • One role is allowed to skip it on purpose. The backfill job uses backfill_user (BYPASSRLS) because it must walk every tenant.

In this repo: V4__vehicles_rls.sql, TenantSession.java, and the "RLS fails closed" checks in the integration tests.

Envelope encryption

What it means: never encrypt your data with the master key directly. Ask KMS for a fresh data key, encrypt the data with it locally, and store only the wrapped (KMS-encrypted) copy of that key next to the data. To read, ask KMS to unwrap it. The master key never leaves KMS.
  1. Create a vehicle: GenerateDataKey returns the key in plain and wrapped form.
  2. Encrypt VIN, plate and owner name with AES-256-GCM using the plain key, then discard it.
  3. Store the ciphertext and the wrapped key (dek_wrapped) in the same row.
  4. Read: Decrypt unwraps the key, the service decrypts the fields. A small cache avoids one KMS call per row on lists.

One data key per row limits the damage of any single key leaking to that row.

In this repo: FieldCipher.java. Users without the vehicle:read-pii permission never trigger a decrypt at all.

Encryption context

What it means: extra labels (here tenant and vehicle) that must match exactly at decrypt time. They are not secret, but they bind a ciphertext to the thing it belongs to. KMS records them in its audit logs.

The same two labels also go into the AES-GCM "additional authenticated data", so a ciphertext copied into another row or another tenant fails to decrypt. The IAM and key policies can require these labels, which turns "someone used the key with no context" into a denied, logged event.

In this repo: FieldCipher.context(), plus the policy conditions in infra/modules/kms and infra/modules/app_access.

Blind index

What it means: a way to search encrypted data for an exact match without decrypting it. Store a keyed hash (HMAC) of the VIN in its own column; to search, hash the VIN you were given and compare hashes.

The hash includes the tenant id, so the same VIN looks different in each tenant. It only supports exact matches, not prefixes or fuzzy search, and the HMAC key must be kept secret and treated as long-lived.

In this repo: BlindIndex.java, column vin_bidx.

Centralized authorization

What it means: code asks one place "is this caller allowed to do X?", and never checks roles itself. Roles map to permissions in a single policy class, so changing who can do what is one edit, and swapping in an external policy engine later does not touch the controllers.

Zero-downtime backfill

What it means: encrypting rows that already exist, while the service keeps running, with no maintenance window. The trick is to change the database in small steps that each work with both the old and new code.
  1. Expand. Add the new nullable columns and build indexes with CREATE INDEX CONCURRENTLY so writes are never blocked. Old code is unaffected.
  2. Dual-read deploy. The new service writes encrypted data and reads either form. A row's encrypted_at being empty means "still plaintext".
  3. Backfill. A job encrypts old rows in small batches. Ciphertext is written and plaintext erased in one statement, guarded by encrypted_at IS NULL, so it is safe to run twice or in parallel. KMS calls happen outside any open transaction, so row locks last milliseconds.
  4. Contract. Only when nothing is pending, a manual script drops the plaintext columns. It refuses to run while any row is unencrypted.

In this repo: V2 and V3 migrations, BackfillService.java, db/contract/drop_plaintext.sql.

Key policy vs IAM policy

What it means: KMS asks two questions and both must say yes. The key policy belongs to the key itself. IAM policies belong to the caller. A permission granted in only one place does nothing.

This repo's key policy has three statements:

  • Let IAM decide. Delegates everyday permissions to IAM policies.
  • Admins cannot use the key. The role that manages the key is explicitly denied encrypt and decrypt. Whoever can change the key cannot read the data (separation of duties).
  • Context is required. Any decrypt or data-key request without an encryption context is denied.

The service's IAM policy then grants exactly two actions, GenerateDataKey and Decrypt, on one key, only when the context keys are tenant and vehicle. An explicit deny always beats an allow.

In this repo: infra/modules/kms, infra/modules/app_access.

Key rotation

What it means: KMS can replace the key's secret material every year. Old ciphertext still decrypts (KMS keeps old material), and new data uses the new material. You do not re-encrypt anything. Here it is switched on in Terraform.

Secrets Manager

What it means: passwords live in a managed store, not in config files or environment variables. Terraform generates random database passwords and stores them as one secret per database role; the service reads only its own at startup, and IAM controls who may read which one.

Caveat: Terraform's state file also holds the generated passwords, so real deployments keep state in an encrypted remote backend.

Who owns what: Terraform vs Flyway

What it means: Terraform builds infrastructure (the key, the database server, the network). Flyway migrations build the schema (tables, indexes, RLS policies) when the app starts. Mixing the two causes drift, so each owns its own layer.

Run it

Needs Docker. On macOS, brew install docker docker-compose colima && colima start.

docker compose up -d --build        # app + postgres + floci (local AWS emulator)
python3 scripts/smoke.py            # 18 end-to-end checks, including the backfill
mvn verify                          # unit tests + Testcontainers integration tests

Try it by hand:

T=$(curl -s "localhost:8080/dev/token?tenant=$(uuidgen)&roles=MANAGER")
curl -s -XPOST localhost:8080/api/vehicles -H "Authorization: Bearer $T" \
  -H 'Content-Type: application/json' \
  -d '{"make":"Honda","model":"Civic","year":2021,"vin":"1HGCM82633A004352","plate":"C456XYZ","ownerName":"Ana Perez"}'

Look at what the database really stores: the VIN, plate and name columns are unreadable ciphertext.

Infrastructure walkthrough

The AWS side is built with OpenTofu (same language as Terraform). The same modules apply to floci locally and to real AWS.

infra/
  modules/
    iam/          app role (the service) and key-admin role (manages, never uses)
    kms/          key + alias, rotation on, three-statement key policy
    app_access/   least-privilege IAM policies for those roles
    network/      VPC, 2 private subnets, security groups (db reachable only from the app group)
    database/     RDS Postgres 17, TLS-forcing parameter group, 3 Secrets Manager secrets
  envs/
    local/        floci endpoints, short deletion windows
    aws/          real provider, 30-day key deletion window, deletion protection (validated only)
  1. Start floci with RDS support. export COMPOSE_FILE=compose.yaml:compose.aws.yaml then docker compose up -d floci. The override mounts the Docker socket so floci can start a real Postgres container.
  2. Apply the infrastructure. cd infra/envs/local && tofu init && tofu apply. Creates the key, roles, policies, network, database and secrets.
  3. Create the database roles. python3 scripts/rds_bootstrap.py reads the passwords from Secrets Manager and creates app_user and backfill_user.
  4. Start the service against it. docker compose --profile aws up -d --build app-aws. It reads its credentials from Secrets Manager, and Flyway creates the tables on the RDS instance.
  5. Check it. python3 scripts/smoke.py --aws runs the same 18 checks against this stack.

Continuous integration runs verify (all tests), tofu fmt and validate for both environments, CodeQL analysis of the Java and the workflow files, and dependency review. main is protected by a ruleset that requires verify, both CodeQL analyses and dependency review, and blocks high-severity CodeQL alerts. The tofu checks only run when infra/ changes, so they are not required.

What this does not prove

Read this before trusting the local stack for anything.

floci does not enforce policies. It stores key policies and IAM policies but does not evaluate them. A GenerateDataKey call without an encryption context succeeds locally, and real AWS would deny it. Use the local stack to check that resources and wiring work, and use real AWS or the IAM policy simulator to check that permissions deny what they should.

Other known gaps: the local setup lets the service read the database owner secret so Flyway can migrate (production should run migrations as a separate job), the backfill job has no IAM role of its own yet, and the secrets use the default AWS-managed key instead of a customer-managed one.
